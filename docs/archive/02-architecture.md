# 02 · 架构

## 三条分层

```
┌─────────────────────────────────────────────┐
│  UI 层      RN / Compose / 别的 —— 可替换    │  只渲染，不含业务逻辑
├─────────────────────────────────────────────┤
│  桥接层     引擎生命周期、会话、能力裁剪、审批 │  与 UI 框架无关，可单测
├─────────────────────────────────────────────┤
│  Runtime    Kotlin：进程、rootfs、前台服务、   │  每平台 ≤1500 行
│            通知、权限、无障碍                  │
├─────────────────────────────────────────────┤
│  引擎       Node + dsh（独立进程）            │  难活都在这
└─────────────────────────────────────────────┘
```

**核心原则：桥接层做厚，UI 层做薄，Runtime 层做薄且稳定。**

UI 框架是可以换的，Runtime 不是。所以业务逻辑一律不进 UI，也一律不进 Runtime——它的位置在桥接层和引擎里。

## Runtime 的七个接口

每个平台（Android / iOS / 未来鸿蒙）只实现这七个，多一个都不要：

```
install()    解包 rootfs 与 node
start()      拉起进程 + 前台服务
stop()
status()     运行中 / 启动失败 / 已停止（含失败原因）
logs()       日志流
notify()     通知（含进度胶囊）
fs()         分享菜单进来、SAF 授权
```

**判据：任何"顺便在这里算一下"的念头都要掐掉——那是业务逻辑，回到引擎侧去。**

## UI ↔ 引擎的协议

- 传输：本地 loopback HTTP + WebSocket 事件流（终端走 PTY / abstract unix socket）
- 类型：从引擎的 OpenAPI 生成，**不手写 interface**
- **能力协商**：客户端连上来先问"你支持哪些事件、哪些审批动作、哪些预设能力"，宿主按自己的能力回

```
→ hello { client: "rn/1.2.0", platform: "ios" }
← capabilities {
    host: "phone" | "desktop",
    events: ["run.started","run.finished","approval.requested", ...],
    actions: ["approve","reject","steer", ...],
    presets: [...],
  }
```

**UI 只渲染协商结果，禁止出现 `if (Platform.OS === 'android')`。**
这条守住了，iOS 端才不是二等公民。

## 跨设备的三种语义

"手机和电脑是一个身份的两个身体"这句话，落到实现上是三件不同的事，必须拆开：

| 语义 | 做什么 | 需要的机制 | 成本 |
|---|---|---|---|
| **镜像** | 手机看电脑那个会话，只读或遥控 | 远程连接 | 低 |
| **分叉** | 从某条消息岔出一条手机支线，带上下文，文件用引用 | 跨宿主 fork + 引用协议 | 中 |
| **委派** | 各自独立，需要对方的东西时把子任务派过去 | 跨宿主 subagent / 工具调用 | 低 |

**主线是「分叉 + 委派」，镜像是特性。**

委派必须双向：

- 手机 → 电脑：`delegate(pc, "把那个仓库的测试跑一遍")`
- 电脑 → 手机：`delegate(phone, "拍一张发票，OCR 后存到文档工作区")`

第二条才是真正对等的东西——电脑没有相机、没有你的口袋、不在会议室里。

## 文件引用

会话里引用别的宿主上的文件，存成：

```
dsh://<host-uuid>/<path>
```

手机上的模型看到的是"这个文件在另一台设备上，需要内容时调 `fetch_file(ref)`"，背后是一次按需拉取（带用户确认 + 大小上限）。

**文件永远只有一份，住在它原本的宿主上。**

## 单 writer

一个会话只有一个 writer（它所在的宿主），其他设备是 reader + 指令发送者。

你在手机上给电脑上的会话发一条消息，本质是**向那个会话投递一条输入**，由宿主执行。这样并发、锁、一致性全部绕开，直接复用 DSH 现有的 `steer` 语义。

> 踩坑记录：DSH 现在同一个 `$DSH_HOME` 被两个实例打开会出现会话锁竞争和 `session_projcache` 双写。**"一个世界一个 writer"是现有实现的隐含前提**，跨设备设计必须尊重它。

## 配对，而不是云端账号

每台设备本地生成密钥对，配对时交换公钥 + 一个共享密钥（扫二维码即可）。之后会话索引在这两台设备之间直接同步：同局域网走 LAN，不同网络走中继。端到端加密，服务器看不到内容，也不需要知道你是谁。

好处：**"连起来"不引入任何外部依赖。** 没有服务器宕机、没有账号注销、没有"我的数据去哪了"。删掉配对关系，两台设备立刻回到完全独立。

## 降级红线

> **任何跨设备能力，都必须有本地降级路径。不允许出现"连不上电脑所以用不了"的功能。**

示例：电脑离线时，会话列表里显示"电脑 · 离线 · 上次同步"，手机自己的一切功能不受影响。

这条守住了，"手机是独立宿主"才不是一句口号；守不住，就会退化成遥控器。

## 数据模型

| 实体 | 归属 | 是否同步 |
|---|---|---|
| Identity（模型渠道、偏好、插件授权） | 账号级 | 是，端到端加密 |
| Device（设备、公钥、配对关系） | 账号级 | 是 |
| Host（一台能跑引擎的机器） | 设备级 | 是，仅元数据 |
| Workspace（目录 + 能力契约） | 宿主级 | 否，只同步索引 |
| Session（会话） | 宿主级 | 只同步元数据与状态，正文按需拉 |
| File | 宿主级 | 否，靠引用 |

一条规则：**执行永远本地，文件永不离家。**
