# 01 · 产品定位

## 一句话

**手机上一个属于你的 agent，它还有一台电脑可以叫。**

不是"在手机上也能用你的 agent"，是"手机上有一个 agent"，这两句的差别就是整个产品的差别。

## 场景判断

一个场景值得做手机端，要同时满足三条：

1. 手机有这个场景需要的能力，而电脑没有（在场、随身、离线、相机、触达、操作别的 App）
2. 这个能力是 agent 完成任务**所必需**的，而不是"顺便也能看"
3. 没有成熟替代品

按这个标准筛：

| 场景 | 手机独有能力 | 替代品 | 工程代价 | 结论 |
|---|---|---|---|---|
| 通勤/外出遥控电脑 | 随身 + 移动网络 | 已有 3–4 个成熟项目 | 中 | 需求真实，但红海；**作为特性做，不作为主架构** |
| 长任务值守与审批 | 锁屏触达、随时介入 | 基本没有 | 高（推送是硬骨头） | **最值得做**，但 v1 不做远程推送 |
| 手机本机跑 agent | 无电脑可用 | 少且脆弱 | 极高 | **v1 主线** |
| agent 操作手机 | 手机是 agent 的手 | 无 | 极高（无障碍/Shizuku） | 有想象力，不是 v2 之前的事 |

**结论：v1 押"手机本机"，v2 押"值守审批"。** 遥控是顺手带上的能力，不是叙事中心。

## 为什么纯通知做不成产品

通知是单向、低带宽、低信任的通道。用户收到"任务完成了"，下一句一定是"然后呢？"。如果答案是"打开 App，进聊天页，翻到那个回合"，通知只兑现 10%，剩下 90% 是打开一个在手机上天然劣势的聊天界面。

更麻烦的是商业上：纯通知没有护城河，本质是 webhook 路由器。官方一内置推送，或者用户自己接个机器人，你就没了。

**所以通知必须配"就地决策"：批准/拒绝/插话，一步完成，不用进聊天。**

## 为什么"值守审批"值得做

手机端真正该优化的是：**从收到通知到做完决策，中间隔几次点击。理想是一次。**

判断一个审批功能是否成立的标准很简单——**能不能只看锁屏那一屏就做决定**。命令原文、风险等级、改动摘要，缺一个就不成立。信息密度不够的审批，用户只能盲批或打开 App 看半天，那是负价值。

## 非目标

明确不做，避免反复纠结：

- ❌ 工作区同步（用引用 + 委派替代）
- ❌ 云端账号体系（用设备配对）
- ❌ iOS 本机引擎（物理限制）
- ❌ v1 的远程推送（前台服务 + 本地通知足够）
- ❌ v1 的插件市场（只内置有限预设）
- ❌ 多端同时编辑同一会话（单 writer）
- ❌ 手机端做代码开发的主场景（体验让给电脑）

## 命名

**对外：锦囊　对内：`dsh-palm`**

| 层级 | 名字 | 职责 |
|---|---|---|
| 品牌 | 锦囊 | 被记住、被传播、撑起词汇体系 |
| 技术 | `dsh-palm` | GitHub / npm / 命令行里一眼看出血缘和场景 |

副标题：**装进口袋的智能体**
口号：**有事，交给锦囊**

### 为什么是这两个

- "锦囊"后面永远跟着"妙计"，不需要解释就知道里面装着办法
- 是一个能画出来的东西（小布袋），图标和桌宠都好做
- **词汇体系长在名字上**，不用另造词

### 词汇表

| 动作 | 话术 |
|---|---|
| 安装预设 | 收一个锦囊 |
| 切换预设 | 换个锦囊 |
| 分享预设 | 把锦囊送给朋友 |
| 首次引导 | 先收三个锦囊：文档、票据、生图 |
| 离线 | 锦囊暂时打不开 |

用户说"给我装个票据锦囊"——这句话是自解释的。

### 风险

"锦囊"是通用词，商标显著性弱，第 9/42 类大概率有人注册。不硬砸钱注册，靠"产品名 + 副标题"做搜索占位。`dsh-` 前缀是社区事实上的命名空间，不是官方商标，但 README 必须写清"社区项目，与 DeepSeek 无关"。
