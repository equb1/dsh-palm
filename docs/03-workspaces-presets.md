# 03 · 工作区与预设

## 工作区 = 能力契约

工作区不只是一个目录，是**一份结构性约束**：装了哪些工具、能碰哪些路径、能不能联网、能不能执行代码。

```yaml
workspace: 手机/文档
host: phone
root: ~/workspaces/docs
tools:   [docx.*, xlsx.*, pdf.read, pdf.render, ocr, file.move]
sandbox:
  fs:   [~/workspaces/docs, /sdcard/Download:ro]
  net:  deny                    # 文件不出本机
  exec: python-limited          # pandoc / python-docx 需要执行环境
surfaces: [camera, share_intake]
model_policy:
  needs: [long_context >= 64k]
  prefer: deepseek-chat
```

## 执行点：工具注册层，不是提示词

> ⚠️ **实现状态（2026-11-02）**：这条是目标设计，**真 dsh 宿主上还没生效**。
> 真 dsh 只有三档权限（read-only / workspace-write / danger-full-access），没有工具白名单；
> 我们现在的预设只映射成它的 `agentPreset`（standard / ptc / minimal / cordis）。
> 所以「模型看不见没给它的工具」目前只在 mock 引擎和协议层成立，**别把它当安全边界**。
> 落地路径：等上游的会话级工具裁剪，或先用「一个工作区一个 `$DSH_HOME`」的 profile 过渡。

**模型不是"被告知不要用 shell"，而是根本看不见 shell 这个工具。**

在 prompt 里写"请不要用别的工具"是安全剧场；按契约裁剪工具表再交给模型，才是真的。两者的安全性和可预测性差一个量级。

## 粒度：会话级，不是工作区级

切换预设不应该等于切换整个世界——那样会话列表会断、记忆会断，用起来很累。

正确做法：**预设挂在会话上，工具表按会话裁剪。**

手机上可以同时有"文档会话"和"生图会话"并存，各自挂不同工具，共用同一个工作区根目录和同一条会话列表。用户点"新建"时选预设，已有会话保持它创建时的预设不变。

### 落地路径

| 阶段 | 做法 | 代价 |
|---|---|---|
| 过渡（v1 可接受） | 一个工作区一个 profile（独立 `$DSH_HOME`） | 会话列表要自己合并，跨工作区不共享记忆 |
| 目标 | DSH 支持会话级工具集裁剪 | 需要上游配合 |

> 如果 dsh 的插件加载还是 host 全局的，这就是必须补的一块。补上了"预设"才有地基。

## 预设三级

手机端装第三方插件 = 把任意代码装进用户口袋。按风险分层开放：

| 级别 | 内容 | 风险 | 开放时机 |
|---|---|---|---|
| **L1 声明式** | 纯配置：prompt + 选工具 + 选模型 + 界面 | 无代码 | **v1 就开放**，可分享成二维码 |
| **L2 技能包** | 指令 + 参考资料 + 资源，无代码 | 低（可能藏 prompt 注入） | v2 |
| **L3 代码插件** | npm 包，注册工具/UI | 高（任意执行） | v3，签名 + 权限声明 + 审核 |

L1 才是"豆包式智能体"：用户写个 prompt、勾几个工具、选个模型，就能生成一个预设分享出去。**生态成本几乎为零，且不怕事故。v1 把 L1 做透，别急着开 L3。**

## 内置的五个预设

按"电脑做不到"筛：

| 预设 | 触发方式 | 工具 | 典型活 |
|---|---|---|---|
| 文档助手 | 分享文件 / 会话 | docx、xlsx、pdf、文件移动 | 改格式、提取表格、批量改名 |
| 票据管家 | 拍照 | 相机、OCR、xlsx 写入 | 发票收据 → 结构化表格 |
| 读图问答 | 相册 / 拍照 | 视觉模型、图片裁剪 | 看说明书、看板书、看菜单 |
| 生图 | 会话 | 图像生成、图库保存 | 配图、头像、海报草稿 |
| 会议纪要 | 录音 | 录音、转写、日历 | 录音 → 摘要 → 待办 |

共同点：**输入来自手机的感官，输出回到手机的其他 App。** 这就是"手机是独立分身"落到功能上的样子。

## 三个必须提前定的事

### 一、别把预设硬绑模型

豆包那种"智能体 = 某个模型"的做法，用户换个渠道就废。

预设只声明**能力需求**（要视觉、要 64k 上下文、要便宜），运行时按需求匹配用户已配好的渠道。

### 二、切换预设不能丢上下文

用户在会话里聊了半小时，中途想加个生图能力，不能逼他新开一个会话重讲一遍。

**预设要支持会话内升级**（挂载额外工具包），而不是只能"新建时选定"。

### 三、"手机不写代码"≠"不需要执行环境"

处理 docx/xlsx 必然要跑 pandoc、python-docx。所以 `exec: python-limited` 这一层必须留——只是**模型看不见 shell，只能通过受限的文档工具间接用到它**。

不留这层，文档预设做不出来。

## 一个人做，就别做平台方

预设一多就变成应用商店，要承担质量、安全、兼容、审核、下架。

**v1：只内置有限预设，不开市场。v2：开放 L1 的分享（二维码 / 链接）。v3：才谈签名插件。**

等产品稳定了，再考虑"预设管理平台"——那是后话。
