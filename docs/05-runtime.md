# 05 · 运行时与打包

## 进程模型

```
App 进程（RN）
  └─ 前台服务（Kotlin，dataSync）        ← 保活、通知、进度胶囊
       └─ 引擎进程（Node + dsh）          ← 主进程，事件循环
            ├─ worker_threads             ← 解析类重活
            └─ 子进程池（pandoc / python） ← 转换类重活，可杀
```

**重活必须离开主进程。** 引擎在解析大 JSON、算 diff、做长文本流式修复时，同进程里的本地 HTTP/WS 会一起卡住——用户看到"界面卡死"，但任务其实在跑。这在 agent 产品里是致命的误判。

## 资源账本（量级，装机后实测校准）

| 组件 | 磁盘 | 常驻内存 | CPU 特征 |
|---|---|---|---|
| node（arm64，strip） | 45–55MB | 40–70MB | 空闲接近 0 |
| dsh 引擎 + 几个插件 | — | 80–150MB | 网络等待为主，突发解析 |
| proot + 精简 rootfs | 90–130MB | 20–40MB | 极低 |
| python3-minimal + 文档库 | 40–55MB | 30–60MB（用时才起） | 解析时突发 |
| ML Kit OCR | 15–20MB（进 APK） | 30MB（用时） | 原生线程，不占 JS |
| RN + Expo 运行时 | 8–15MB | 60–100MB | 渲染为主 |

**稳态约 250MB 内存 / 250–300MB 磁盘。**

对比：dsh-go 的包 195MB，出现过 850MB 的异常基线。**要防的是后者，不是前者。**

## 三处真正的瓶颈

### 一、单线程事件循环被堵

对策：解析类走 `worker_threads`，转换类 spawn 子进程，WS 通道加背压、大 payload 分块。

### 二、子进程失控

一个 pandoc 吃满一个核、一个 python 脚本泄漏内存，手机上就是发热 + 被系统杀。

对策：**子进程统一走调度器**——并发上限 2、nice 值调低、超时强杀、内存超阈值重启。**别让插件随便 `spawn`。**

### 三、宿主存活等级不够

Android 按 adj 回收，前台服务没配对就在后台被清。

对策：`startForeground` 用对 type（`dataSync`）、`stopWithTask=false`、OEM 白名单引导做进首次启动流程。

## rootfs：三条路线，选中间那条

| 路线 | 做法 | 体积 | 代价 |
|---|---|---|---|
| A 完整 rootfs | Ubuntu + node + python + git 全塞 | 180–220MB | 省心，但首装劝退 |
| **B 精简 rootfs** | Ubuntu base + node + bash/coreutils，文档库做成可选层 | **120–150MB** | 需要自己做分层 |
| C 原生 node | 二进制放进 `lib/arm64-v8a/` 直接 exec，用 toybox 当 shell | 60–80MB | 要改引擎对 POSIX 的假设，费工 |

**v1 选 B。C 那套（二进制伪装成 `.so` 绕过 API 29 的 exec 限制）是 Termux 走通的路，理论上能砍一半，但一个人别在 v1 碰。**

## 镜像：手机上永远不构建

```
CI（GitHub Actions）
  ├─ 构建 base 层   → base-v3.tar.zst   (sha256)
  ├─ 构建 docs 层   → docs-v2.tar.zst   (sha256)
  └─ 发布 manifest.json（层列表 + 哈希 + 依赖）
              ↓
手机：下载 → 校验哈希 → 解包到版本目录 → 切换软链
```

### 四个好处

1. **构建可复现**：脚本进仓库，谁都能重建，出问题能 diff
2. **引擎独立发版**：改一个 python 库发 5MB 的层，不是 200MB 的 APK，**也不用等商店审核**
3. **可回滚**：版本目录并存，坏了切回上一个软链
4. **首装可分批**：APK 带 base 层保证立刻能用，其余按需下载

### 目录布局

```
<app-data>/
├── runtime/
│   ├── base-v3/
│   ├── docs-v2/
│   ├── current -> base-v3+docs-v2      # 合并视图（软链或合并目录）
│   └── staging/                         # 下载解包中
└── data/                                # 可写状态，永远在层之外
    ├── home/                            # $HOME，会话、插件、配置
    ├── workspaces/
    └── logs/
```

### 两条铁律

1. **层与层用统一的根目录合并解包**，别各自成树——否则基础文件重复占空间
2. **可写状态永远在层之外**，bind 进去——换层不动数据

## 只读基础层

Android 上拿不到 overlayfs，但可以做到近似：

- 基础层解包后**约定只读**（不做 chmod，靠代码约束）
- 可写目录单独 bind 到 `$HOME` / 工作区
- proot 的 `-b` 叠加即可

效果：插件写不坏系统文件，换层不会冲突。

## 尺寸预算（红线，超了就砍功能，别砍架构）

| 指标 | 上限 |
|---|---|
| 首装下载 | ≤ 150MB |
| 装完占用 | ≤ 300MB |
| 空闲内存 | ≤ 250MB |
| 峰值内存 | ≤ 450MB |
| **UI 可交互**（不等引擎） | ≤ 1 秒 |
| 引擎可用（冷） | ≤ 15 秒，且只在开机后第一次发生 |
| 装一个文档预设的增量 | ≤ 50MB |

后两条是 2026-11-01 真机实测之后改的（见 [08-verification.md](08-verification.md)）：
proot 下引擎启动 13.7s，其中 10.3s 是 proot 的税，裁插件只能省 23%。
**所以目标从"引擎快"改成"界面不等引擎"**，引擎靠常驻把 13 秒藏进开机后第一次。

守住这些数字，产品在 6GB 中端机上就是能用的；守不住，再好的功能也留不住人。

## 冷启动顺序

```
1. UI 起来（本地缓存的会话列表立刻可见）
2. 前台服务起
3. 引擎进程起（异步，进度显示在启动卡上）
4. 连上后拉最新，覆盖缓存
```

**UI 永远不阻塞等引擎。** 引擎起不来时，界面显示失败原因 + "重试 / 安全模式 / 看日志"，而不是一个转圈。

> 实测修正：引擎冷启动在 proot 下要 13.7 秒，所以第 1 步必须真的"立刻"——
> 首屏不能等任何一次网络请求，只能读本地缓存。这条从"体验优化"升级成"硬要求"。
