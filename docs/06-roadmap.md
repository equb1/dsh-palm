# 06 · 路线

## 四阶段

| 阶段 | 做什么 | 产出 | 为什么排在这 |
|---|---|---|---|
| **0** | 假引擎 + UI 骨架 | 笔记本上跑一个 mock 引擎，RN 端把会话、聊天、审批、预设切换全画出来 | **一行 Kotlin 都不用写**，第 2 周就能拿给人看 |
| **1** | Android 宿主 | 七个接口的 Kotlin 实现 + 前台服务 + 通知 + 文档预设跑通 | 产品的地基，也是"手机是独立宿主"这句话的证明 |
| **2** | iOS 遥控器 | 纯 JS 客户端，连 DSH Remote | 工作量约 Android 的 1/3，且不碰引擎 |
| **3** | 鸿蒙 | 首选遥控器形态（ArkTS 薄客户端） | 最后做，不参与当前架构决策 |

## 阶段 0：假引擎（1–2 周）

### 做什么

`packages/mock-engine/` 是一个 Node 服务，行为完全仿真真引擎：

- 会话列表、历史分页
- 流式输出（按 token 喂，带思考过程）
- 工具调用卡片、回合折叠
- 审批事件（带命令原文 + 风险等级 + diff 摘要）
- 预设切换、能力协商
- 断线、重连、离线只读

### 验收

- [ ] 在 iOS 模拟器和 Android 真机上都能完整走完一次对话
- [ ] 审批卡只看一屏就能做决定（找 3 个人盲测）
- [ ] 断网后列表不空屏，显示"离线 · 上次同步"
- [ ] 流式输出滚动不掉帧
- [ ] 换一个引擎地址就能连真引擎（协议一致）

### 为什么先做这个

一个人做项目，**能持续拿到可见的进展比架构正确更重要**。这一步让你在没有原生复杂度的情况下，把产品最值钱的部分（交互）验证完。

## 阶段 1：Android 宿主（3–4 周）

### 做什么

- `modules/` 里的七个接口：`install / start / stop / status / logs / notify / fs`
- rootfs base 层的解包、校验、版本切换
- 前台服务 + 通知渠道 + Android 16 进度胶囊
- 分享菜单接入、SAF 授权
- **文档预设的垂直切片**：拍照 → OCR → 写 xlsx → 分享出去

### 验收

- [ ] 冷启动到可输入 ≤ 3 秒
- [ ] 引擎崩溃后能自动拉起，界面不崩
- [ ] 杀掉 App 后任务继续跑（前台服务生效），回来能看到进度
- [ ] 尺寸预算全部达标（见 [05-runtime](05-runtime.md)）
- [ ] 文档切片：一张发票从拍照到分享，全程不超过 4 步

### 一个切片，不是一堆功能

**v1 只做"文档"这一条链路做深**，不做宽。docx、xlsx、pdf 都能碰听起来很美，但一个都做不精，用户一次就流失了。

## 阶段 2：iOS 遥控器（2–3 周）

### 做什么

- 纯 JS：Noise IK 用 `@noble/curves` + `@noble/ciphers` 实现
- 只支持 DSH Remote，不做 SSH
- 会话列表、聊天、审批、进度
- 本地通知（iOS 允许的那部分）

### 验收

- [ ] 能在 iPhone 上完成一次完整对话 + 一次审批
- [ ] 不出现 `if (Platform.OS === 'android')`（走能力协商）
- [ ] 后台切换回来能重连并拉到最新

## 阶段 3：鸿蒙

**放到最后，且不参与当前架构决策。**

三种技术栈对鸿蒙都是"另起一摊"：RN 没有官方支持，Compose Multiplatform 没有，只有 Flutter 有 Flutter-OH（dsh-go 走过）。所以无论现在选什么，鸿蒙到时候都是单独一次评估。

大概率形态：**遥控器**，用 ArkTS 写一个薄客户端，只跟 RN 端共享协议 schema。

## 不建议在 v1 做的事

| 不做 | 原因 |
|---|---|
| 远程推送 | 前台服务 + 本地通知覆盖 80%；推送留到 v2 |
| 插件市场 | 一个人的注意力最稀缺，做平台方会把自己拖死 |
| 工作区同步 | 无底洞，且用户真正要的是上下文连续 |
| 手机操控（无障碍） | 权限链太长，v2 再说 |
| 多主机管理 | 先把单主机走通 |
| 桌面端 | 有人要，但不是现在 |

## 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 一个人维护，节奏断 | 项目死 | 阶段 0 先出可见成果；每个阶段都要有"能给人看"的东西 |
| OEM 后台杀进程 | 核心功能失效 | 首次启动就做白名单引导，别等出问题才教 |
| rootfs 太大劝退 | 留存杀手 | 分层 + 按需下载，首装 ≤150MB 是红线 |
| 会话级工具裁剪要上游配合 | 预设体系卡住 | 先用 profile 过渡，别把架构赌在这一条上 |
| RN 原生模块腐烂 | 升级即地狱 | 原生 ≤1500 行 + 只放 `modules/` |
| 鸿蒙/上游变化 | 计划失效 | 只承诺 Android，别的都是"可能" |

## 一条工作原则

**别信推演，先做 30 分钟真机验证。**

这个领域里已经有 AI 写的可行性分析被维护者当场否掉的先例（"实际上鸿蒙是可以适配的，并且已经成功跑起来了"）。任何"某平台能不能跑起来"的结论，都值得拿真机验一遍再下判断——包括这份文档里的。
